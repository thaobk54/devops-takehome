# Part 5a: Karpenter for GPU inference (EKS)

- `ec2nodeclass-gpu.yaml`: a dedicated `EC2NodeClass` for accelerated nodes, using AL2023. Karpenter picks the NVIDIA AMI variant, nodes use IMDSv2 only, and the gp3 disk is large and fast.
- `nodepool-gpu.yaml`: `gpu-spot` (weight 100) and `gpu-on-demand` (weight 10). Both carry the `nvidia.com/gpu:NoSchedule` taint, use `WhenEmpty` consolidation, allow disrupting only 1 node at a time with a peak-hours freeze, and have GPU/CPU/memory limits.
- **API:** `karpenter.sh/v1` / `karpenter.k8s.aws/v1`, checked against the Karpenter v1.15 docs. It is validated **server-side** against the real CRDs by `scripts/50-validate-iac.sh`, plus policy tests in `tests/static/test_karpenter.py`.

**Spot vs on-demand for AI inference.** GPU spot capacity typically costs 60–70% less, and inference is mostly stateless, so a lost replica can be recreated. That makes spot the right default for horizontally scaled, latency-tolerant serving. Two things work against it. First, a spot reclaim gives only about 2 minutes' notice, while a GPU pod can take several minutes to pull a multi-GB image and load the model, so capacity drops by more than one pod's worth during that window. Second, popular GPU families run out of spot capacity in a region more often than CPU families. The design hedges on both. Spot is preferred, but diversified across several families and AZs. On-demand is the automatic fallback through weights. Consolidation only removes *empty* nodes, so a request is never cut off for bin-packing. For strict latency SLOs, keep a small on-demand baseline that covers minimum traffic (a pod-level preference or a separate Deployment) and let spot absorb bursts. Fully on-demand only makes sense for stateful or long-running jobs that can't checkpoint.
